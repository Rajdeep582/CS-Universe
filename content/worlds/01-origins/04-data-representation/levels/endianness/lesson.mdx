<Step id="hook" section="hook" title="Big-endians and little-endians">

In *Gulliver's Travels*, two nations go to war over which end of a boiled egg to crack. In 1980 Danny Cohen borrowed their names for an argument in computing: when a number takes several bytes, **which byte goes first in memory?**

</Step>

<Step id="intuition-order" section="intuition" title="Same number, two orders">

The 32-bit value `0x01234567` has four bytes: `01`, `23`, `45`, `67`. Memory is addressed byte by byte, so they must be put in *some* order at addresses $a, a+1, a+2, a+3$:

- **Big-endian**: most significant byte first — `01 23 45 67` (like writing digits left to right).
- **Little-endian**: least significant byte first — `67 45 23 01`.

</Step>

<Step id="formal-def" section="formal" title="Definitions">

A multi-byte value of $n$ bytes $b_{n-1} \dots b_0$ (with $b_{n-1}$ most significant) stored at address $a$:

| Order | Address $a + i$ holds |
|---|---|
| Big-endian | $b_{n-1-i}$ |
| Little-endian | $b_i$ |

Endianness affects only the order of **bytes** within a value — not the bits inside a byte, and not the order of characters in a string or elements in an array.

</Step>

<Step id="formal-who" section="formal" title="Who uses which">

| System | Order |
|---|---|
| x86 and x86-64 | Little-endian |
| ARM, RISC-V | Little-endian in practice (ARM can switch) |
| Network protocols (IP, TCP headers) | Big-endian — "network byte order" |
| Java class files, PNG, JPEG | Big-endian |
| ZIP, BMP, most Windows formats | Little-endian |

C programs convert with `htonl`/`ntohl` ("host to network long" and back).

</Step>

<Step id="worked-example" section="worked-example" title="Reading a hex dump">

A file contains the bytes `2C 01 00 00` where a 32-bit length is expected.

- Read as little-endian: `0x0000012C` = **300**.
- Read as big-endian: `0x2C010000` = 738,263,040.

Only one of those is a plausible length, which is exactly how engineers recognise the byte order of an unknown format. A 16-bit value `00 01` is 1 big-endian but 256 little-endian.

</Step>

<Step id="tradeoffs" section="tradeoffs" title="Does either order win?">

| Little-endian | Big-endian |
|---|---|
| The low byte is at the same address whatever the width — reading a 32-bit value as 16 or 8 bits still gives the low part | Hex dumps read naturally; sorting byte strings sorts big-endian integers |
| Natural for adding multi-byte numbers from the low end | Matches network protocols, so no conversion there |

Neither is better overall; what matters is agreeing at every boundary between systems.

</Step>

<Step id="pitfalls" section="pitfalls" title="Common misconceptions">

<Callout kind="warning">**"Little-endian reverses the bits."** Only the bytes are reversed; each byte's bits are unchanged.</Callout>

<Callout kind="warning">**"UTF-8 text has an endianness."** UTF-8 is a byte sequence; UTF-16 and UTF-32 do have one (hence the BOM).</Callout>

<Callout kind="warning">**Writing raw structs to a file or socket.** The receiving machine may have a different byte order (and padding). Serialise explicitly in a fixed order.</Callout>

</Step>

<Step id="context" section="context" title="The holy war">

Danny Cohen's 1980 note *On Holy Wars and a Plea for Peace* (IEN 137) named the two camps and pleaded for agreement at interfaces. The Internet settled on big-endian headers; the PC market settled on little-endian processors — so every network stack converts.

</Step>
