<Step id="hook" section="hook" title="Designed on a placemat">

In September 1992, Ken Thompson and Rob Pike sketched an encoding for Unicode on a placemat in a New Jersey diner. That design, **UTF-8**, is now used by the large majority of web pages — because it kept every old ASCII file valid while reaching all of Unicode.

</Step>

<Step id="intuition-variable" section="intuition" title="Short codes for common characters">

Storing every code point in 4 bytes (UTF-32) is simple but wastes space on English text. UTF-8 uses **1 to 4 bytes**: ASCII characters keep their single byte; other characters take 2, 3 or 4 bytes. The first byte announces how many bytes follow.

</Step>

<Step id="formal-utf8" section="formal" title="The UTF-8 bit patterns (RFC 3629)">

| Code point range | Bytes | Pattern (x = payload bits) |
|---|---|---|
| U+0000–U+007F | 1 | `0xxxxxxx` |
| U+0080–U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800–U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000–U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

Continuation bytes always start `10`, so a decoder dropped into the middle of a stream can find the next character (**self-synchronising**). The shortest form is mandatory; longer "overlong" forms are invalid.

</Step>

<Step id="formal-utf16" section="formal" title="UTF-16 and byte order marks">

**UTF-16** stores BMP code points as one 16-bit unit and the rest as a **surrogate pair**: subtract 0x10000, split the 20 bits into high and low 10 bits, and add them to 0xD800 and 0xDC00. Because units are 16 bits, UTF-16 files have a byte order; a **BOM** (`U+FEFF`) at the start shows it: `FE FF` big-endian, `FF FE` little-endian. UTF-8 needs no BOM (it may appear as `EF BB BF`).

</Step>

<Step id="worked-example" section="worked-example" title="Encoding € by hand">

€ is `U+20AC` = `0010 0000 1010 1100` (16 bits) → needs the 3-byte form (U+0800–U+FFFF).

1. Split the 16 bits as 4 + 6 + 6: `0010` · `000010` · `101100`.
2. Fill the pattern: `1110 0010` · `10 000010` · `10 101100`.
3. In hex: **E2 82 AC**.

In UTF-16 it is one unit, `20AC`; 😀 (`U+1F600`) is `D83D DE00` in UTF-16 and `F0 9F 98 80` in UTF-8.

</Step>

<Step id="tradeoffs" section="tradeoffs" title="UTF-8, UTF-16 or UTF-32?">

| | UTF-8 | UTF-16 | UTF-32 |
|---|---|---|---|
| Bytes per code point | 1–4 | 2 or 4 | 4 |
| ASCII compatible | Yes | No | No |
| Byte-order issues | None | Yes (BOM) | Yes |
| Used by | Web, Linux, files, JSON | Windows APIs, Java and JavaScript strings | Some internal processing |

For East Asian text UTF-16 can be smaller (2 bytes vs 3 per character); for everything mixed with ASCII markup, UTF-8 usually wins.

</Step>

<Step id="pitfalls" section="pitfalls" title="Common misconceptions">

<Callout kind="warning">**"Bytes = characters."** "€" is 3 bytes in UTF-8. Truncating a UTF-8 string at a byte limit can cut a character in half.</Callout>

<Callout kind="warning">**Mojibake.** Reading UTF-8 bytes `C3 A9` (é) as Windows-1252 shows "Ã©". The bytes are fine; the decoder guessed the wrong encoding.</Callout>

<Callout kind="warning">**"UTF-8 can be 6 bytes."** The original 1993 design allowed up to 6; RFC 3629 (2003) limits UTF-8 to 4 bytes and `U+10FFFF`.</Callout>

</Step>

<Step id="context" section="context" title="UTF-8 everywhere">

HTML5 recommends UTF-8; JSON (RFC 8259) requires it for interchange; Rust and Go strings are UTF-8; Python 3 source files default to it. Since 2019 Windows can also use UTF-8 as a process's code page.

</Step>
